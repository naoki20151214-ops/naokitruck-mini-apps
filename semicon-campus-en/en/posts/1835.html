On October 1, 2026, Texas Instruments (TI) announced that it has expanded support for Zephyr, an open-source operating system for embedded devices, across its broad embedded semiconductor portfolio, including MCUs, MPUs, and wireless connectivity devices. TI says it aims to make it easier to move to its products while keeping existing Zephyr codebases and toolchains. However, this is TI's description of its product and development plans. It does not mean every product can be migrated without changes, or that every feature is available at the same time. TI official announcement

What was announced

The core of the announcement is that TI is extending Zephyr beyond specific evaluation boards and a few wireless chips to general-purpose MCUs, wireless connectivity products, real-time MCUs, and MPUs. TI says it will provide upstream-first code review, CI/CD on public GitHub, validated releases, migration guides, backward-compatibility information, and long-term maintenance information. These aim to reduce the need to rebuild drivers, build settings, and test procedures when switching chips. TI official announcement

As a concrete example, TI's SimpleLink Low Power Zephyr SDK V3.7.0-01.00.00-GA was posted on July 27, 2026, and lists the CC2340R5, CC2340R5MODA, CC2755P10, CC2755P20, and CC2755R10 as supported products. This SDK is a release based on TI's own downstream fork, and TI has also stated its plan to integrate it into the main Zephyr tree (mainline) in the future. So we cannot assume that all features were already merged into mainline at the time of the announcement. TI SimpleLink Low Power Zephyr SDK

What is Zephyr RTOS?

RTOS stands for "real-time operating system." It focuses on running tasks such as reading sensors, controlling motors, and handling communications within set time limits. Unlike a smartphone OS that centers on rich screen features, it is an OS for running multiple tasks reliably on devices with limited memory and power.

Zephyr is built on a small kernel for resource-constrained embedded devices and supports many CPU architectures, including Arm Cortex-M, Cortex-A, and Cortex-R, RISC-V, x86, ARC, and Xtensa. It uses a modular design, which makes it easy to combine only the features you need. Zephyr official technical documentation

Key technical terms

  • Devicetree: A way to describe the hardware on a board, such as the CPU, memory, GPIO, and communication circuits. It makes it easier to manage board-to-board differences as settings without heavily rewriting source code.
  • Drivers: Software that lets the OS and applications control hardware such as UART, SPI, I2C, sensors, and wireless circuits. With a common driver model, higher-level applications are easier to reuse.
  • CI/CD: A development practice that automatically runs builds and tests every time code changes, so problems are found early. With public CI/CD in place, it is easier to check support status and bugs.

TI's official guide also explains that it uses Twister and Ztest to validate Zephyr. These are frameworks for repeating tests across many boards and configurations. In other words, an important part of this announcement is not just "there are working samples," but building a development foundation that keeps checking support over time. TI's Zephyr guide

Why this matters in embedded development

In embedded products, switching to a different chip part number or a different chip maker can affect the OS, drivers, communication stack, bootloader, build settings, and even the test environment. Rebuilding software from scratch every time the hardware changes increases not only development time but also the burden of long-term maintenance.

If you can use a common RTOS, APIs, build system, and test procedures across a wider range of chips, it becomes easier to develop derivative models in a product line. This is especially true when one company uses several products, from low-power wireless MCUs to higher-performance MPUs, since software assets may be shared. This matches the value TI promotes, "migration while keeping existing Zephyr workflows," but it does not mean an independent organization has proven reduced migration effort or better performance. TI official announcement

Past challenges and where this fits

Zephyr aims to work across many chip makers, but a common OS does not make hardware differences disappear. An official Zephyr issue from March 2025 recorded technical challenges: peripheral support was scattered across several TI series, and many peripheral blocks were not yet supported. This "broad portfolio support" is best read as a move to expand coverage and the development setup against the background of those past challenges. Official Zephyr issue

Also, Zephyr's official release information lists 4.4.0 as the latest stable release on April 14, 2026, while 3.7.0 is the LTS release from July 26, 2024. Version 4.5 is listed as a planned release for October 2026, and the planned date should not be confused with the actual release date. The support status of TI's downstream SDK, TI-managed repositories, and Zephyr mainline each need to be checked separately. Zephyr release information

Limits, and what to check before mass-production adoption

One thing to watch in this announcement: the phrase "broad portfolio" alone does not pin down support for every part number, every peripheral, and every application. Even with Zephyr, items such as pin assignments, clocks, interrupts, DMA, power states, proprietary accelerators, boot configuration, and wireless certification need extra checks for each chip.

Also, even when TI describes an SDK as "production grade," that is TI's own positioning of that SDK. It does not automatically guarantee the reliability, performance, power consumption, security, or regulatory compliance of the final product. The EU Cyber Resilience Act (CRA) support that TI mentions also does not mean the final product automatically meets its legal obligations. The product maker still needs to handle vulnerabilities, documentation, conformity assessment, and so on.

  • Whether the board definitions and peripheral drivers for the target part number cover the features you need
  • Version and patch differences between TI's downstream SDK and Zephyr mainline
  • Test reports and measured results for performance, power consumption, and wireless certification
  • Who provides security fixes, and who is responsible for maintenance, including after the product is discontinued
  • Whether pins, power, and boot configuration match between the evaluation board and the production board

What to watch next

Going forward, the focus will be which part numbers and peripherals TI actually merges into Zephyr mainline, and how much the gap between the downstream SDK and mainline narrows. For Zephyr 4.5, we also need to confirm whether it was actually released on schedule. In addition, it matters how well the public CI/CD and test reports cover the specific boards and product configurations that developers use.

This announcement shows that a chip's value depends not only on CPU performance and price, but also on a software foundation that can be used for years and on its connection to the developer community. When considering adoption, do not decide based on the phrase "Zephyr support" alone. It is important to check features for each part number, SDK maintenance, test results, and the relationship with mainline.
