On September 28, 2026, Fraunhofer AISEC in Germany announced that it had completed functional validation of silicon prototype chips for its OpenTitan-based RISC-V Secure Element and had entered the technology transfer stage. Going forward, it plans to offer not only the complete secure element but also individual security IP blocks in a licensable form that can be built into SoCs, ASICs, and chiplets. Fraunhofer AISEC announcement

One thing to note here is not to treat the announcement date and the date functional validation was completed as the same. The publication date is September 28, but it is not stated when the validation work on the prototype chips itself was completed. Also, what we can confirm is only the stage of "finishing functional validation and moving on to licensing and joint development." It is not an announcement that mass-produced parts have already been adopted in customer products.

What does this news mean?

Semiconductor security features are not something you can simply add with software after a product ships. Mechanisms that make sure only the correct programs run at startup, and circuits that handle secret keys safely, need to be built in from the chip design stage. If design companies build security features from scratch every time, development time, verification burden, and the risk of design errors all increase.

Fraunhofer explains that the implementation, developed by AISEC, EMFT, and IIS under the Trusted Electronic Bayern Center framework, was manufactured using GlobalFoundries' 22nm FD-SOI technology and prototyped in Dresden. This announcement goes beyond presenting a research-stage design. After confirming functions on real silicon, it moves toward IP and integration support for porting it into customers' designs. Related Fraunhofer IIS announcement

In other words, the core of the news is not that "a new encryption method was invented." It is that a path has been shown for offering OpenTitan-based security functions as building blocks customers can easily reuse in their own SoCs and ASICs. For chiplets, too, it may widen the option of combining security functions as a dedicated die or dedicated block. However, the specific connection method, packaging, certification boundary, and license scope are not settled by this announcement alone.

Technical terms made simple

What is a Root of Trust?

A Root of Trust is the hardware or software foundation that a system first trusts as "correct." For example, to check that the program a smartphone or embedded device loads after power-on has not been tampered with, you first need a trustworthy checker.

In the OpenTitan design, a hard-to-change silicon ROM is the starting point, and it uses public keys and similar means to verify the signature of the next boot stage. That stage then verifies the software that runs after it, and so on, chaining trust together. By running only authorized code, tampering can be detected even before the OS or applications start. OpenTitan official security documentation

Secure boot and key management

Secure boot is a mechanism that checks the digital signatures of firmware and the bootloader at startup and runs only legitimate code. Key management refers to the mechanisms for safely storing and using the keys used for that signature check and the secret information unique to each device.

Fraunhofer lists a hardware Root of Trust, secure boot, secure key storage, device identity, authentication, and secure firmware updates as features. These may look like separate functions, but in practice they are closely linked. To identify a device, confirm the correct owner or server, and accept only authorized updates, startup trust, keys, authentication, and update management must be designed together. OpenTitan security model specification

What is post-quantum cryptography?

Post-quantum cryptography refers to encryption methods designed to withstand the threat that future quantum computers may break the public-key encryption widely used today. Fraunhofer says this platform supports both conventional cryptography and post-quantum cryptography.

However, this primary announcement does not confirm which algorithms were adopted, which operations are accelerated in hardware, or what the performance and power consumption are. The phrase "post-quantum ready" alone does not mean complete security against every quantum computer attack or that product certification has been obtained.

How OpenTitan relates to the Fraunhofer implementation

OpenTitan is an open-source silicon Root of Trust project. It covers not only secure boot but also device authentication, key management, provisioning, lifecycle management, firmware updates, and a verification approach that includes side-channel analysis and fault injection. This allows a trust boundary inside the chip to be built without relying on software alone.

On the other hand, the general design and security model described in OpenTitan's official documents cannot simply be equated with Fraunhofer's implementation specs. From this announcement alone, we do not know which OpenTitan revision or configuration was used, which features were added or changed, or whether it has undergone third-party evaluation or certification. Even in OpenTitan's official specs, the architecture specification for integrated IP is listed as a target for a future release.

Fraunhofer points to benefits such as shorter development time, lower technical risk, and a smaller external attack surface. However, these are effects and expectations described by Fraunhofer. They do not show independent customer deployments or quantitative comparisons with other security IP. Completing functional validation also does not automatically guarantee resistance to physical attacks, mass-production yield, long-term supply, third-party certification, or performance in customer products.

What to watch next

Going forward, first, we need to see what the license actually includes. The value customers get will vary greatly depending on which IP blocks, RTL, software, verification environment, and design services are provided. Second, it matters whether customer chips using the implementation are announced or reach mass production. Between functional validation of a prototype chip and mass-production IP used by multiple customers over the long term, there is additional verification and certification.

Third, we need to assess the post-quantum cryptography methods, performance, memory usage, power consumption, and update methods. For chiplets, the focus will also include protecting die-to-die communication, trust boundaries within the package, initial key provisioning, and how ownership is transferred. This announcement is an important step in moving a validated security foundation into commercial IP, but it is best read with some distance: it is not news that mass-production adoption has been completed.
